1Architecture Overview

The system uses Nebius Soperator to deploy a Slurm cluster on Kubernetes. Two GPU nodes (1x L40S each) handle training via DDP over Ethernet. GPUs are shared between training and inference by scaling Soperator workers up/down.

10Evaluation Results

Three evaluation methods assess the fine-tuned model on 1,000 held-out samples (10% eval split, never seen during training).

Key Results

The LoRA fine-tuned model achieves 83.5% accuracy vs the base model's 49.4% - a +34.1 percentage point improvement as judged by Claude Sonnet. Automated metrics confirm the improvement: ROUGE-L doubles from 0.21 to 0.43, and BERTScore F1 improves from 0.84 to 0.91.

11Future Improvements

Areas identified during the project that would improve the pipeline - deferred due to time or cost constraints:

GapDescription
No eval_loss trackingtrain_loss and epoch_avg_loss only. No validation loop means you can't detect overfitting during training. Add a val_dataloader and log eval_loss every epoch.
No resume from checkpointIf the job crashes, training restarts from epoch 0. Add --resume_from_checkpoint arg that loads adapter weights and skips to the right epoch/step.
Epoch-only checkpointingWith ~440 steps/epoch, a crash at step 430 loses 9+ minutes. Add save_steps logic inside the step loop.
No config validationIf a typo in the YAML sets lora_r='sixteen', the float() cast fails with a cryptic error. Add Pydantic or cerberus schema validation.
No data versioningDataset loaded from a JSON file with no hash or version. Running the same script with a modified dataset produces different results silently.
No fault toleranceIf one DDP process dies, the job fails entirely. torchrun --rdzv-backend=etcd enables elastic training and node failure recovery.
MLP modules not targetedOnly attention projections (q/k/v/o) are LoRA targets. Adding gate_proj, up_proj, down_proj typically improves quality substantially.
No gradient accumulationEffective batch is only 4 sequences. Adding gradient_accumulation_steps=4 would reach effective batch 16 with no memory increase.
Labels cross example boundariesPacked sequences concatenate multiple examples. The model trains to predict across EOS tokens, which can confuse the next example's instruction token. Fix: use attention masks that mask cross-example positions.

12Conclusion & Architectural Decisions

This project demonstrates an end-to-end pipeline for distributed LoRA fine-tuning on Nebius cloud infrastructure - from cluster provisioning through training, serving, and automated evaluation. Several architectural decisions shaped the design:

Why Soperator (Slurm-on-K8s)?

Running Slurm inside Kubernetes via Soperator provides the job scheduling semantics that ML workloads need (multi-node GPU allocation, job queuing, gang scheduling) without leaving the Kubernetes ecosystem. This avoids managing bare-metal Slurm clusters while keeping Kubernetes-native tooling for everything else - MLflow, TensorBoard, vLLM inference, and Grafana all deploy as standard K8s resources alongside Slurm workers.

Why LoRA Instead of Full Fine-Tuning?

With only 2x L40S (48 GB each), full fine-tuning of even an 8B model would require aggressive sharding (FSDP/DeepSpeed ZeRO-3) and would be impractically slow over Ethernet. LoRA reduces trainable parameters to ~52 MB, making DDP over TCP viable - each GPU holds the full frozen model plus a small adapter, and only adapter gradients are communicated via NCCL all-reduce. This keeps the Ethernet interconnect from becoming a bottleneck.

Why DDP Over Ethernet (Not FSDP)?

The cluster uses standard Ethernet, not InfiniBand. With LoRA, the all-reduce payload is tiny (~52 MB per step), so DDP communication overhead is negligible even over TCP. FSDP would shard model parameters across nodes, requiring constant high-bandwidth parameter gathering - exactly the pattern where Ethernet becomes a bottleneck. DDP with LoRA is the natural fit for Ethernet-connected GPU clusters.

Why Shared GPU Ownership?

With only 2 GPUs, dedicating separate GPUs to training and inference isn't possible. Instead, the system switches modes: Soperator workers hold GPUs during training, then scale to 0 to release them for vLLM inference pods. FluxCD reconciliation must be suspended during inference to prevent the slurm-operator from respawning workers. This is a deliberate trade-off - operational simplicity over running both simultaneously - appropriate for a 2-GPU demo cluster.

Why Config-Driven Training?

All hyperparameters live in YAML config files rather than being hardcoded or passed as CLI arguments. This makes experiments reproducible - each run's resolved config is saved alongside the adapter - and enables easy model switching. The same training script handles Llama 3.1 8B and Qwen 2.5 14B simply by pointing to a different config file, with no code changes required.

Why Claude Sonnet as Judge?

Automated metrics (ROUGE-L, BERTScore) measure surface and semantic similarity but cannot assess whether a response actually answers the instruction correctly. Using Claude Sonnet via Vertex AI as an impartial binary judge provides a more meaningful accuracy signal - and avoids the circular problem of using the same model family for both generation and evaluation. The 90/10 train/eval split ensures the judge evaluates on samples never seen during training.

Key Takeaways

LoRA fine-tuning on a 2-node Ethernet cluster is practical and effective: 97.9% GPU utilization, 1-hour training time, and a +34.1% accuracy improvement over the base model. The Soperator + Kubernetes architecture provides a clean separation between training (Slurm) and inference (K8s Deployments) while sharing the same GPU pool. The pipeline generalizes to larger models - Qwen 2.5 14B trains on the same cluster with only a config change.
