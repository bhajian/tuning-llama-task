1Architecture Overview

The system uses Nebius Soperator to deploy a Slurm cluster on Kubernetes. Two GPU nodes (1x L40S each) handle training via DDP over Ethernet. GPUs are shared between training and inference by scaling Soperator workers up/down.

2Infrastructure Setup

Deployed via Terraform using the Nebius Solutions Library. Soperator provisions a Slurm cluster on Kubernetes with GPU worker nodes, shared NFS storage, and SSH-accessible login nodes.

Deployment Steps

9Evaluation Results

Three evaluation methods assess the fine-tuned model on 1,000 held-out samples (10% eval split, never seen during training).

Key Results

The LoRA fine-tuned model achieves 83.5% accuracy vs the base model's 49.4% — a +34.1 percentage point improvement as judged by Claude Sonnet. Automated metrics confirm the improvement: ROUGE-L doubles from 0.21 to 0.43, and BERTScore F1 improves from 0.84 to 0.91.

10Future Improvements

Three areas were identified during the project that would improve the pipeline but were deferred due to time or cost constraints:

Smarter Data Handling

The current pipeline blindly packs samples into fixed 2048-token blocks. A pack boundary can land in the middle of a sample, truncating the instruction or answer and creating noisy training signal. A smarter approach would respect sample boundaries during packing, drop or re-bucket samples that don't fit cleanly, and filter out low-quality or duplicate entries before training begins.

Evaluation During Training

Currently evaluation only happens after training completes. Periodic validation loss and metric evaluation during training — logged to MLflow — would enable early stopping, catch overfitting sooner, and provide richer experiment comparison across runs.

Hyperparameter Sweep

The LoRA config (rank=16, alpha=32, lr=2e-4) was chosen based on common defaults. A systematic sweep over LoRA rank, learning rate, batch size, and number of epochs would likely yield better accuracy — but requires significant GPU time and cost on multi-GPU clusters.
